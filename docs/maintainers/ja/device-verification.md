# 実機検証

FoldLab で記録を取り、実機のブラウザがどう動くかを確かめます。この資料は開発者向けにリポジトリ内で管理し、公開ドキュメントサイトには含めません。

Pixel 10 Pro Fold の実機計測は、これから進める段階です。Mock やデスクトップの Device Mode はUIづくりやテストに役立ちます。実機の記録が揃うと、日常的な操作でブラウザがどう動くかを、さらに確かめられます。実機検証が完了する前の暫定的なnpm公開は許容しています。

## 実機で記録を取る

FoldLab の Device inspector から始めます。Environment notes に、機種・Androidのバージョン・ブラウザの完全なバージョン・日付・関係する設定を残しておくと、後で記録を見返しやすくなります。

シナリオを選んで記録を始め、操作を行います。画面が落ち着いた後のサンプルも取ってから記録を止め、JSONファイルを出力します。

| シナリオ     | 確かめたいこと                                         |
| ------------ | ------------------------------------------------------ |
| 通常表示     | layout/visual の寸法、領域の原点と境界                 |
| ズームとパン | 複数の倍率、0以外の offset、倍率1への復帰              |
| キーボード   | 開閉前後、入力欄の位置、viewport の設定                |
| 回転         | 縦から横、横から縦への変化、領域の順序と隙間           |
| 折りたたみ   | 開く・半折り・閉じる。それぞれの姿勢と領域を別々に記録 |

キーボードでは、`resizes-visual`・`resizes-content`・`overlays-content` を別の条件として試します。FoldLab で viewport の meta 設定を切り替え、ブラウザが実際に反映したかも記録します。ズームは有効にしたまま、操作中と画面が落ち着いた後の両方を残します。

境界を比べるときは、ブラウザの丸めとして原則1 CSS pxの差を考慮します。元の計測値は変更せずに残しておくと、後から別の方法でも比較できます。

出力には、形式とライブラリのバージョン、UA、メモ、イベント時刻、生の layout/visual/segments、4×4の範囲で調べたCSS比較値、公開 snapshot が入ります。APIが `available` でも snapshot が `fallback` になる記録は、ブラウザから値を読めた一方で、座標変換を確認できていないことを表します。

記録は端末内で扱います。FoldLab は最大1,000件のサンプルをメモリに保持し、古い記録を削除した件数も出力します。

## 計測結果をテストに取り入れる

新しい座標変換を有効にする前に、整理した実機記録をテスト用の fixture に加え、変換式と適用条件をまとめます。こうしておくと、今後の変更を確かめるための具体的な基準になります。値が一致しないときは、寸法の比率から倍率を決める前に、座標系の関係を確認します。

プロジェクトのチェックは、次のコマンドで実行できます。

```sh
vp check
vp test
vp run -r build
vp run docs#validate
vp run test:e2e
vp run test:package
```

APIの利用状況、フォールバック、配置、入力の保護、同期取得とRAF、解除・再購読、SSR・hydration・共有時の責務を確認します。まとめて実行したい場合は、`vp run ready` を使えます。
