## A shared coordinate frame [#contract]

A coordinate is most useful when you know where it starts. In Folyx, viewport, segments, and gaps all use CSS px measured from the upper-left corner of the layout viewport. Browser Provider reads the layout dimensions from `innerWidth` and `innerHeight`.

The visual viewport describes the part of the page currently in view. Its size and offset can change as someone zooms, pans, or opens the keyboard. Those changes are why a shared CSS px unit alone isn't enough to establish that two measurements have the same origin and coordinate frame.

Folyx checks the frame as well as the rectangle bounds. It leaves the measurements at their reported scale rather than guessing a correction from size ratios, `devicePixelRatio`, or `visualViewport.scale`.

## How version 0.1 handles Browser measurements [#policy]

Browser Provider uses the reported CSS px coordinates when layout and visual frames coincide within browser rounding. It checks that:

- Visual scale is finite and positive, and `abs(scale - 1) * max(viewport.width, viewport.height)` is at most 1 CSS px.
- The `offsetLeft` and `offsetTop` values are zero.
- The dimensions agree within 1 CSS px, allowing for browser rounding.

The combined segment bounds must also agree with all four viewport edges within 1 CSS px. Browser Provider clamps overflowing edges to the viewport, keeping internal boundaries, gaps, and already in-bounds fractional coordinates unchanged. It does not expand regions that stop just short of the viewport. If clamping would leave any region with zero or negative width or height, the whole segment reading is withheld. Bounds alone do not establish the coordinate frame.

For example, a Pixel 10 Pro Fold normal-display recording reports an 851 × 817 viewport, a visual scale of `1.0001797676086426`, and two touching 426 × 817 segments whose right edge reaches 852. Browser Provider returns widths of 426 and 425, preserving the internal boundary at x = 426. The public snapshot has `segments.source: "browser"`, `layout: "horizontal"`, and `gaps: []`. Layout viewport dimensions stay unchanged, and FoldLab retains the original measurements for comparison.

If the visual viewport is unavailable or the frames differ, such as during zoom or a keyboard resize, Browser Provider keeps the raw segments out of the public state. A known layout viewport becomes one fallback region. If the viewport is also unknown, the region list stays empty. API availability remains `available` when the raw geometry could be read.

Version 0.1 supports coincident frames with this bounded rounding correction; other coordinate transforms aren't enabled yet. The Pixel 10 Pro Fold recording reproduces the original normal-display fallback in regression tests. Hardware confirmation of the fix, zoom, pan, keyboard behavior, rotation, and folding transitions remain pending. Device names and UA strings aren't used as coordinate rules.

## Following changes and comparing measurements [#diagnosis]

Browser Provider follows window resize, posture change, screen orientation change, page restoration, visibility change, and visual viewport resize/scroll. Visual viewport measurements stay outside the public snapshot.

For a closer look, FoldLab records raw browser measurements alongside the public snapshot. This keeps the original readings available for comparison while Core continues to provide layout coordinates. CSS `env(viewport-segment-*)` is included as an independent diagnostic comparison in FoldLab; it isn't a Core data source.

The Browser Provider uses the current `navigator.devicePosture` and `window.viewport.segments` interfaces. Older interfaces such as `visualViewport.segments` and `getWindowSegments` aren't supported. Feature detection and fallback let the same application code run across browsers, while the measurements it can receive depend on each browser's API support.

For more background on these APIs and coordinate concepts, see the [references](/references).
